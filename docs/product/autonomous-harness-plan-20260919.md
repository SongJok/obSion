# Obsion：自主企业 Harness 产品化总体计划

**日期：2026-09-19。性质：设计与开发合同，不是实施完成报告。**

核查对象：`SongJok/obSion`。固定基线：`24d5503826d1901fe95abe8cb80ebb8466949682`，不是另一个 `open-obsion` 仓库。本文结合GitHub源码、项目状态、实际CI检查和官方产品文档。没有在本次审查中部署项目、运行源码测试、连接企业生产数据或测试真实gVisor集群。来源路径与链接见 `SOURCES.md`。

## 一、结论

继续演进当前仓库，不建议推倒重做、不建议换后端语言、不建议把某家编码产品直接套成拥有全部公司权限的总控入口。

下一阶段目标应是：**在现有统一Harness内部，把预设路由和局部知识调查提升为“任务合同驱动、缺口驱动探索、证据约束、真实隔离执行、持久恢复与受控交付”的企业自主执行系统。**

自主性不等于没有边界。对预授权只读调查和任务隔离区内的计算，系统应尽可能少打断用户；对发消息、建工单、提PR、修改配置等外部副作用，执行既定策略与审批；对当前不允许的生产写入继续禁止。完整性不是任意问题都能答或任意操作都能做，而是每个受支持任务都具备从理解到交付的闭环，且每个不满足的任务都有真实、可操作的终止或等待状态。

## 二、当前仓库的事实与判断

### 2.1 值得保留的资产

`AGENTS.md`明确了一个Python控制面、PostgreSQL事务事实源、Workspace→Thread→Turn→Run→Step→Event持久模型、统一Capability Gateway和Policy。不要按旧蓝图创建第二套后端或Agent循环。[R01]

当前Planner已有分类路由与依赖步骤；`investigation.py`实际实现模型提议SEARCH/READ/STOP、选定资料范围、分页、动作指纹和有限预算；`evidence_gaps.py`实际存在Critic缺失证据补查。这不是完全没有Harness的聊天壳。[R03–R05]

README声明的持久任务、事件、模型网关、证据、权限、审批、记忆、受管查询、Action Gateway、客户端和开源治理，是应逐项验真的现有资产，不应因新的模块名称重新造一遍。[R02]

### 2.2 三个最重要的当前阻断

**实际任务质量尚未过门。** 仓库P1质量门记录的旧候选真实24例为5 PASS、1超时FAIL、18 BLOCKED；评分未校准，P1/Phase99未完成。这些是仓库报告，不是本次重新实测，不是“模型事实准确率20.8%”。此前大量本地测试通过不能替代真实业务质量。[R08–R09]

**当前HEAD远端CI未全绿。** GitHub `quality` 检查为failure。步骤查询显示Python测试步骤success、`npm run lint` failure，后续前端typecheck/test/build被跳过。本次没有取得具体lint错误行，不猜测根因。先修复真实错误、重跑完整链，不把旧状态中的passed字段当当前候选全绿。[R10–R11]

**沙箱有实质基础，但尚未形成可用执行闭环。** README所说不启动容器只是其中一层边界。`sandbox/kubernetes.py`已有真实Kubernetes REST适配、gVisor RuntimeClass、固定镜像digest、无凭据契约、非root、只读根文件系统、无宿主网络/挂载、NetworkPolicy、资源限额及不确定创建对账等实现；同文件明确该切片没有注册Harness能力、禁止生产环境启动。下一步应接通和验证现有实现，而不是声称“没有沙箱”或从零重写。[R06–R07]

### 2.3 自主性差距的准确定位

| 已观察到的实现 | 差距 | 处理 |
|---|---|---|
| Planner按KNOWLEDGE、DATA、ENGINEERING、INCIDENT等生成模板 | 不是通用的基于目标缺口的动作规划器 | 模板作为起始计划，增加动态结果绑定和短视野重规划 |
| evidence_gaps按DOCUMENT/CODE/LOG等类型补查且排除已调用能力 | 有证据类型不代表具备完成业务问题的语义维度；同工具有效后续查询可能受限 | 建Dimension Ledger，按动作指纹去重而不是工具名去重 |
| investigation可换查询与续读正文 | 自主调查主要限定知识域 | 在同一Harness扩展受管代码、Schema、日志、Skill、计算等动作 |
| Python AST，Java/TS保守提取，SQL表名正则 | 不能声称已理解全部Java语义、MyBatis动态SQL、跨服务或线上配置 | 按真实仓库语言与框架建立测试矩阵；区分候选关系与已验证关系 |
| 沙箱合同与K8s/gVisor适配 | 尚未注册Harness；没有本次真实集群验证 | 接通Gateway、Run/Step、生命周期、Artifact并做隔离与故障测试 |
| 项目文件传输首片支持UTF-8普通文件，500文件、总8MiB等边界 | 不是任意规模仓库/二进制/依赖支持 | 公布边界，按真实需求扩展输入协议和供应链，不简单放大限制 |
| README alpha候选与状态文件0.98.0-dev | 产品范围/版本表达有歧义 | 统一可安装范围、真实支持矩阵和发布候选证据 |

以上源码事实分别见[R02–R09、R12]。表中升级是建议，不能据此认定当前代码里已有相同新符号。

## 三、从成熟产品借鉴什么

OpenAI对Codex循环的说明强调模型—工具—真实观察的多次迭代与上下文管理。借鉴点是可重复运行的闭环，而不是一段特别长的提示词。[W01]

Cursor文档明确终端allowlist/自动审查是尽力而为的防护，不是硬安全边界。企业系统需要把资源权限、网络和隔离交给模型外部机制。[W02]

Antigravity展示计划、实现方案、验证记录、差异和截图等Artifact，以及按需加载技能。借鉴点是用户可审阅的工作产品和分层上下文，不是复制界面就能得到相同能力。[W03]

因此定义：

```text
企业Harness = 模型能力 + 上下文构建 + 资源/能力发现
            + 任务与探索循环 + 权限/预算执行
            + 隔离运行环境 + 持久状态与恢复
            + 证据/产物验证 + 用户可控制的工作台
```

模型是否足够强仍需在企业任务上评测；工程机制不能替代模型能力，也不能用更强模型替代所有数据、语义和安全治理。

## 四、目标架构：一套控制面，分离执行边界

```text
Web / 钉钉 / CLI / IDE / API
                │
         现有统一 App Server
                │
       RunIntent / TaskContract
                │
      现有 Harness 内部升级
  ┌────────────────────────────────────┐
  │上下文构建与当前授权                  │
  │Dimension Ledger：知道/缺少/冲突什么  │
  │资源目录 + 能力目录 + 企业关系映射     │
  │探索提案、动态计划、预算与去重         │
  │规则验证、语义复核、停止与交付判定     │
  └────────────────────────────────────┘
                │
        统一 Gateway + Policy
                │
  ┌─────────────┼──────────────┐
知识/Skills/代码/日志     SQL/API/Redis      隔离沙箱Worker
  │                       │                  │
  └──────────── Evidence / Artifact ─────────┘
                │
      授权/时效/合同/验证发布屏障
                │
  结果、可验证部分、待操作卡片、真实回执

横向复用：PostgreSQL事件/检查点/Outbox、模型网关、审计、对象存储、调度。
```

“隔离Worker”是执行面与信任边界的分离，不是新后端语言或第二Agent决策循环。新增逻辑优先放入现有模块。`runtime.py`后续可在特征测试保护下按上下文、计划、执行、验证、发布职责拆分内部代码；不要以拆微服务代替梳理职责。

## 五、真正自主：回答六个问题

### 5.1 要完成什么

任务开始形成TaskContract：目标、输入资料范围、实体、指标/维度、时间及时区、精确性、用户限制、输出类型、允许环境、权限主体、预算与完成判据。

例如统计任务必须固定：人群定义、观察时点、身份/等级取值时点、JOIN关系、去重粒度、筛选、分子/分母、时间边界及一致性要求。不要为了得到数字修改最难的条件。

先探查能查清的歧义；只有授权资料不能决定、且不同选择会改变结果时才问用户。比如可以从活动目录唯一解析活动ID就不追问；“本月活跃”存在两个并存指标口径且未指定时则需要选择。

### 5.2 还缺什么

每个任务维护信息义务，而不是统一强制所有问题都必须有代码和日志。

```text
DimensionRequirement:
  id / kind / hard_or_optional
  expected_scope / as_of / precision
  validation_rule / acceptable_evidence_kinds

DimensionState:
  UNKNOWN / PARTIAL / VERIFIED / CONFLICTED / UNAVAILABLE / NOT_APPLICABLE
  supporting_evidence / contradicting_evidence
  remaining_actions / verification_receipts
```

“查某业务有哪些表”需要表的用途与源码/Schema定位，通常不需要扫描生产日志；“某用户昨晚为何没领奖”需要具体时窗的运行和业务记录，不能仅凭代码解释当作事件结论。

### 5.3 去哪里找

资源目录描述“有什么”，能力目录描述“能如何操作”，企业关系映射描述“业务之间如何连接”。先经过ACL过滤再让模型选择，不能先把所有私密资源喂给模型再要求它保密。

关系例子是设计模式，不是当前企业事实：

```text
业务概念 → 指标/规则 → 服务 → API/符号 → 仓库快照
                             ↓
                       ORM/SQL → 逻辑库表
                             ↓
                  部署配置/CMDB → 实际集群
                             ↓
                       日志/Trace/指标
```

每条关系都有来源、版本、有效期与验证级别；静态推断与线上观察分开保存。没有映射时允许生成探索动作，不允许把猜测永久写成事实。

### 5.4 怎么获取

保留四阶默认探测顺序：本地/DWS企业知识→已审核Skills→相关云效代码→必要生产可观测信息。顺序是探索偏好，不是每个问题都必须执行，也不是权威性等级。充分度研判贯穿各阶。受管数据查询、API、Redis和沙箱是独立执行通道，不是固定“第五阶”。

工具选择不应直接拼任意HTTP或shell。先发现已授权能力与契约，确认参数和目标，然后服务器验证动作，再执行。未知参数可通过安全元数据/Schema探测获取；缺连接则进入等待流程。

计划分成“目标计划”和“下一批可执行动作”。先执行有价值的小批次，读取真实结果再决定后续。无依赖的资料检索可并行；依赖前一步解析的表名、符号或实体的动作必须等待类型化结果绑定。

去重键至少包括能力版本、资源、规范化查询、合同范围、来源快照、时间窗与分页cursor。相同工具不同有效查询可以继续，相同数据换工具不能逃避共享预算。瞬时失败的重试另计attempt并退避；授权失败不能反复试到成功。

初期动作排序使用可解释规则：先排除越权/超预算动作，再比较能否解除关键缺口、证据质量、时效、查询代价和重复程度。不要虚构已经校准的“信息增益概率”。

### 5.5 什么时候足够

完整交付必须同时满足：全部适用硬义务已验证、无关键证据冲突、当前权限与时效符合合同、要求的真实执行已完成、产物通过核验。不得用覆盖80%、confidence0.95、四个来源都调用过作为完整判据。

各来源可分别返回partialFindings和missingDimensions；全局账本合并后重算缺口。多源联合足够时使用综合交付；仍缺关键项时交付已验证部分或明确受阻。复核后的拒绝候选不能当作新的证据重入循环。

验证分工：服务器核验范围、引用与数据不变量，领域验证器核验统计/规则，独立语义复核核验结论是否被支持。它们都有能力边界，因此需要人工校准与独立保留集，不存在一个评分器证明一切正确。

### 5.6 失败后如何继续

```text
可恢复瞬时失败 → 有界重试
查询不合适 → 改查询/换有权限的来源
证据不足 → 补关键义务
证据冲突 → 查版本、时点和适用范围
缺连接/授权/资料 → 持久等待 + UserActionRequest
执行状态不明 → 原操作ID对账，不盲目重复
没有价值的新动作/预算结束 → 安全部分交付或终止
```

高自主性应减少不必要追问，但不能替用户改业务目标、扩大权限、安装未知插件或在无证据时编造答案。

## 六、沙箱：从现有适配器到可用产品

### 6.1 三类工作区

分析工作区接收授权DataResult/文件，运行Python、SQL后处理和报告生成。代码工作区接收固定源码快照，允许修改副本、构建和测试。浏览器工作区执行受限站点的浏览、页面核验及经策略允许的操作。三者使用不同配置与权限，不共享生产cookie、仓库凭据或数据库账号。

当前先把现有Kubernetes/gVisor方案验真，不同时引入多个沙箱厂商/微虚机平台。具体隔离方案仍需按威胁模型和兼容性评测；gVisor不是任意风险的充分解决方案。[W04]

### 6.2 数据与凭据路径

```text
授权SQL/文件读取 → 受管查询/连接器
              → 最小化、脱敏、固定版本的输入Artifact
              → 沙箱计算
              → 输出收集与校验
              → 有ACL的报告/表格/代码diff
```

模型可以提出Python代码，但生产查询由Gateway执行。沙箱内只有完成任务必需的输入，不注入生产凭据、宿主目录、Docker socket或共享登录态。数据出口走独立策略，默认无网络；确有依赖需求时走受审核镜像/依赖包或受管代理，而非任意pip/npm安装。

### 6.3 生命周期与可信回执

在既有模型上补齐：请求→排队→创建→运行→完成/失败/超时→收集→待回收→回收。状态和资源handle持久化；Job创建响应丢失时按同一ID回查，不能重置ID重新执行。

进程退出0只能证明进程正常退出，不能证明业务分析正确。输出文本不能决定可信exit code、输入hash或测试是否实际执行，这些必须由可信执行监督器产生并绑定本次Run。输出文件按路径、类型、数量、大小、恶意内容、敏感信息与当前ACL复查。

Kubernetes NetworkPolicy是否生效依赖网络实现，且允许规则可以叠加。因此真实集群需验证CNI执行、RuntimeClass存在、准入限制、安全字段与网络探针，而不是只检查YAML里写了deny。[W05]

### 6.4 当前保护不能直接删除

现有适配器拒绝production启动。要把沙箱作为正式企业服务提供，应独立形成部署ADR和真实安全验收，明确“生产部署的沙箱服务”和“允许操作生产业务资源”是两件事。不能为了让演示跑通而删掉检查，或失败后回退宿主subprocess。

## 七、可恢复执行与受控操作

保留已有Run/Step/Event与PostgreSQL事实源；新增检查点、Outbox与子任务状态都以其为主。不能仅用FastAPI后台协程模拟持久运行。

执行与外部副作用之间无法通过一个本地数据库事务保证通用exactly-once。实现上采用至少一次调度、稳定幂等键、租约/fencing、外部回执和UNKNOWN对账；没有provider幂等或确认能力时宁可等待人工确认，也不能盲目重发。

生产写入默认禁止。开发/测试环境的PR、工单等沿已有Action Gateway完成：预览差异→不可变审批对象→执行前重验→受管执行→真实回执→必要补偿。审批必须绑定主体、目标、参数/patch hash、风险、有效期；内容变化后重新审批。回滚是新的动作，也需要它自己的权限与语义，不能承诺撤回已发送消息就能消除数据外泄。

取消必须传播到外部查询、沙箱和子任务；失败的清理进入待对账，不能把cancel按钮变色当作已停止。Replay恢复视图，不重放副作用；Fork产生新的执行身份，重新授权。

## 八、上下文、模型、记忆与多Agent

模型职责分为理解、计划、代码生成、综合和复核，并不要求五个不同模型，更不意味着必须五次串行调用。先基于企业任务评测Profile，确定工具协议遵循、长任务一致性、代码执行纠错、时延与成本。绑定模型/端点版本，受密级和预算控制；回退不能跨越数据外发政策。

上下文由当前合同、已验证关键证据、剩余缺口、任务状态与按需工具构成；大型原始数据留在受管文件，不完整塞进模型。压缩保留硬约束、实体、证据指针与版本，不能只保留一句自然语言摘要。

记忆区分偏好、短期工作状态、已验证业务知识与候选假设。组织知识的提升需要Owner审核、来源、有效期与ACL；不能把一次模型成功回答自动写成永久事实。历史回放与记忆召回均检查当前权限。

多Agent应在主循环稳定之后启用：业务定位、代码分析、数据分析、运行时调查可针对独立子问题并行。每个子任务只有父任务允许权限的子集，共享总预算、取消与审计；返回结构化证据，不把多个模型互相赞同当成正确性证明。

## 九、用户体验与“所有操作”的产品合同

简单闲聊直接回答，不强制跑企业探索。低风险已授权查询自动执行；复杂任务显示计划摘要、真实进度、已经证实的发现和缺口，而不是模型原始隐藏思维链。

统一AnswerEnvelope建议包含：任务状态、完成范围、已验证结论、证据引用、口径/时点、Artifacts、操作回执、限制与待用户动作。对普通用户隐藏内部敏感资源和调试细节，对授权管理员提供可操作的诊断。

UserActionRequest需包含：类型、原因、需要的权限或资料、绑定合同版本、恢复条件、失效时间、目标Run。OAuth/凭据在受控配置页完成，只把连接引用交给运行时。用户完成操作后原任务恢复并重验，不要求重新说一遍。

Web、钉钉、CLI、IDE必须共用App Server。钉钉群输出还需受众权限，不能仅凭提问者有权限就在群里公布结果。跨入口追问共享有权限的任务状态，重复回调与事件重连不产生重复动作。

“所有操作”应建立支持矩阵：

| 请求 | 目标行为 |
|---|---|
| 闲聊、解释概念 | 无不必要工具的直接回答 |
| 政策/业务/代码定位 | 有出处、有适用版本的授权查询 |
| 精确统计、分析与报告 | 受管真实查询、隔离计算、可复算产物 |
| 故障分析 | 分开事实、候选原因与缺口，必要时调查运行时证据 |
| 修改工作副本、运行测试 | 沙箱自动执行，真实回执验证 |
| PR、工单、消息等副作用 | 按既定授权与风险执行，必要审批，交付实际回执 |
| 缺资料或连接 | 等待并给可操作卡片 |
| 当前禁止的生产变更 | 明确拒绝，不换工具绕过 |
| 未支持任务 | 坦诚说明范围，并交付可做的安全部分 |

## 十、一条贯穿案例（设计示例，不是本次真实生产调查）

用户：统计近30天某活动老板的任务完成率，按等级分组，解释异常并导出表格。

系统先确定活动、老板身份取值时点、任务完成判定、等级时点与统计窗口。能从已授权规范确定的自动确定，存在实质歧义的请求选择。随后从知识/Skill获得指标方法，从固定代码与Schema核对物理表和枚举，从部署配置确认真实环境。

构建逻辑人群与任务集合，验证JOIN/去重/筛选；Query Gateway以只读身份执行。数据快照进入分析沙箱，Python计算分组指标、检测异常并生成表格。由独立校验检查分子分母、总计、边界与结果复算。需要解释当前异常机制时，才进一步查询真实日志/Trace。

日志未接入仍可交付已验证统计，但必须写明原因分析未完成，并生成连接请求；不能编造根因。用户随后要求修改代码时，将请求转为新的动作合同，在隔离工作副本修改与测试，确认目标与权限后再进入现有PR审批执行路径，绝不直接改生产。

## 十一、开发安排与交付合同

`backlog.json`包含20个工作包、100项开发任务；`phases/H01.md`到`H20.md`提供各自目标任务；`acceptance-cases.json`包含80条尚未执行的场景规格。不是生成好的业务测试代码，也不是已经实施的功能。

阶段分组：H01–H05是事实基线/任务/目录/自主循环/验证；H06–H08是企业知识、代码和问数；H09–H10是沙箱和分析交付；H11–H14是运行时调查、恢复、上下文与统一体验；H15–H18是工具、动作、多Agent和持续任务；H19–H20是独立质量与发布。

H01即开始评测、UI和纵向验收，不把所有测试拖到H19。各阶段至少一个从真实客户端到Gateway到证据/结果的纵向切片。H15浏览器/扩展传输与H17多Agent为需求驱动扩展，不阻塞已定义只读企业V1；未验收则不宣传已支持。

建议首个产品里程碑不是“20阶段全写完”，而是H01–H10中支撑一条真实业务分析链的必要任务通过；并在既有恢复机制下可追踪、可取消。然后增加故障调查和受控PR闭环。

AI编码工具一次领取一个可审查工作包或其子任务，先读当前源码、列复用映射、补失败测试、实现、完整验证与报告。不要更换技术栈，不要新建同名平行接口，不要删测试，不要把生产权限问题当代码问题绕过。建议代码作者与复核者分离，由人持有关键权限与发布决定。

## 十二、发布判据

以下为建议验收政策，不是行业统一标准，也不是当前项目已达成成绩。

技术门：当前候选完整CI通过；生产必需能力无未说明跳过；迁移、升级、恢复、租约、取消、幂等、撤权和隔离反向测试通过。

质量门：保留旧24例做回归；建立至少60例双人标注的评分校准集和至少240例独立业务保留集（知识60、Skill/多源40、代码定位60、精确统计40、运行调查40）。本包80条结构化场景用于指导跨域安全/故障与功能测试，需要落为实际fixture，不能代替上述真实业务集。

建议在业务Owner确认后设置标准可答任务正确完成率≥95%、复杂多源任务≥85%的候选目标，并同时报告样本量、不确定性、失败/阻塞构成及人工介入。它们不是普遍保证；确认集验证不达标就限制支持范围。缺资料时正确部分交付/拒答单独评估，不得混入可答任务成功分子。

精确统计在固定gold数据上必须符合合同定义，关键数字有执行回执；生产数据持续变化时记录一致性边界。操作任务以外部真实状态为准，不能将提出方案、生成diff或点击按钮当完成。

性能先测分任务p50/p95和成本。首进度事件可设约1秒的体验目标，但复杂多源调查、真实代码构建/测试和报告生成不能承诺1秒最终完成。使用无依赖并行、按需上下文、经批准的新鲜度缓存、异步产物来降低成本，不省略必要授权或验证。

安全门：关键反向测试任一失败阻断上线；模型上下文与输出不得出现生产凭据，未经授权的访问/副作用必须被外部边界阻止。有限测试全过不证明对所有未来输入绝对安全，还需威胁建模、持续监测、补丁与红队验证。

最后，只有支持矩阵、真实业务、隔离执行、恢复与发布证据都成立，才把对应范围称为产品级。当前应优先把闭环做实，而不是继续增加“已完成阶段”的数字。
