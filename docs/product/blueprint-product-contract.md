# Obsion 完整产品需求总纲

更新：2026-09-15。来源：项目原始 `goal.txt`，重点第四、第五部分及后续产品化范围决策。
本文件是需求索引和验收边界；已有代码或单项测试通过不等于产品验收完成。

## 产品目标

员工从 Web、钉钉、IDE、CLI 或 API 提问，由一个助手自主理解目标、选择方法、读取当前
授权企业资料、补查缺口并交付可核查结果。平台统一管理知识、数据、代码、日志、指标和
运行环境能力。模型、MCP或客户端是可替换组件，公司的长期资产是上下文、能力、证据、
语义、权限、记忆及评测数据。

V1 打通企业知识、企业问数、线上问题调查三个场景；在隔离环境内逐步支持项目开发。
自主性始终受目标、权限、时间、步骤与费用限制。生产写入、自动合并和自动发布不属于
本次默认权限；治理范围见既有 Action Gateway 合同。

## 第四部分：总体技术架构的验收要求

| 层 | 产品职责 | 必须证明 |
| --- | --- | --- |
| Experience | 一个助手，多客户端入口 | 同一身份、任务、答案、引用和取消/恢复状态，不存在独立客户端 Agent 后端 |
| App Server | 统一任务协议 | Thread/Turn/Run、流式事件、审批、产物和幂等重连统一进入服务端 |
| Harness | 理解→计划→执行→观察→验证→反思→响应 | 有界补查与重规划；失败、等待补齐、取消和恢复都持久化 |
| Registries | Agent、Skill、Capability 的版本目录 | 每个 Run 固定执行版本；Skill 提供方法，不能替代企业事实来源 |
| Gateway | 企业能力访问入口 | MCP/HTTP/SDK/gRPC/SQL等适配统一经过授权、风险、审批、脱敏、秘密管理、限流和出口控制 |
| Intelligence | Code、Data、Logs、Knowledge、Runtime | 外部调用、时间、版本、完整性和证据可回溯；开发适配器明确标注 |
| Evidence / Control | 事实和治理底座 | 逐条事实有来源；最终答案独立复核；所有真实调用保留 Policy 和审计 |

仓库 ADR 对蓝图后半部分技术选型作出的明确收敛继续有效：**单一 Python 控制面，
PostgreSQL 为事务与事件事实源**。V1不引入第二种后端语言，也不把Kafka/ClickHouse当作
基础依赖。蓝图第四部分的职责分层不要求拆成重复后端或不同语言。

## 第五部分：Harness 核心模型的验收要求

| 核心对象 | 用户含义与持久约束 | 验证要求 |
| --- | --- | --- |
| Workspace | 围绕真实工作目标组织任务、文件、证据、报告、决策和记忆 | 空间隔离、成员权限、产物引用和来源撤权 |
| Thread | 一个持续问题，支持创建、继续、分叉、归档 | 分叉保留不可变历史，继续不能丢失用户选择与约束 |
| Turn | 用户一次输入，一个 Turn 可有多个 Run | 输入来源与主体明确，追问保持任务上下文 |
| Run | 一次有目标、计划、模型、预算和终态的执行 | 等待审批/用户、重规划、完成/失败/取消的状态真实；支持恢复与回放 |
| Step | 一次可观察的执行或验证步骤 | 参数来自真实目录/上一步结果，逐次授权；不得凭空构造完成事实 |
| Event | 统一追加式运行协议 | 顺序、关联、重连游标与审计可核对，事件不泄漏凭据 |

原始观察、计划、工具请求/结果、Evidence、审批、重规划和最终输出属于运行轨迹。
“反思”保存缺什么、为什么继续/停止、还需哪些资料或操作，不要求展示模型内部思维链。
“自我进化”产生可评测的版本候选，经过冻结任务集和回归后推广，不可自己放宽权限或测试。

## 对用户新增要求的收敛

企业事实每次提问都需要当前授权外部查证。索引帮助发现目标，不能冒充本轮外部读取。
优先利用已接入的 MCP；协议选择服从可靠性与供应商支持，不绕过 Gateway 去直接访问。
资料缺失时进行有界、多维度补查，仍不足则说明已查范围和具体补齐条件。缺少连接或权限
时提供可操作提示，不宣称已接通。用户明确上传的原生资料保留独立阅读入口和来源标签。

## 按产品闭环交付

| 阶段 | 主要用户成果 | 当前验收状态 |
| --- | --- | --- |
| P1 | 问题理解准确、正文进入模型、真实答案可独立评测 | 进行中；独立评分接线及单个真实案例已验证，校准、总体质量、性能和执行版本证明未通过 |
| P2 | 钉钉知识与三个授权云效仓库可持续查证、跨文件补查 | 未完成；不能用目录读取成功替代完整资料/代码问答 |
| P3 | 沙箱内自主查改测、恢复、独立验收和补丁交付 | 未完成；需要真实隔离及适用任务集，云效代码执行遵循明确只读范围 |
| P4 | 可信问数、Metric/Log/Trace/Deployment/Git联合调查与报告 | 未完成；需要真实只读来源及独立金标案例 |
| P5 | 企业身份隔离、连续运行、备份恢复和受控交付 | 未完成；正式Phase99技术与操作方门禁保留 |

数量、正确率、延迟、恢复和试运行门槛以[P1—P5详细需求](productization-p1-p5-requirements.md)
及[用户范围决策](productization-scope-decisions.md)为准：云效代码仅只读，用户明确允许
不运行云效仓库代码；对应原始动态验收保留NOT_RUN及例外原因，不计PASS，也不扩展到
其他沙箱、安全或业务质量门禁。不能因为现有实现难以达到而降低适用门槛。
每阶段必须有实现、测试、文档、迁移或无需迁移说明、
验证报告和架构门。每个增量分次提交并与GitHub main核对，失败回归必须修复后再收尾。
