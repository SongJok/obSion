## 二、本轮产品范围与默认约束

本轮使用 **P1—P5 五个产品化阶段**，保留现有正式 Phase 编号和 Phase 99 发布门禁。

- **优先场景：** 企业知识与代码问答。

## 三、五个 Phase 的功能与验收要求

### Phase P1：修复问答根因，建立可信验收基线

**阶段目标：让系统正确理解问题、保留有效证据，并能够真实测量自己的不足。**

| 目标 | 功能标准 | 自主验收与通过条件 |
|---|---|---|
| P1.1 统一意图与多轮上下文 | Web、钉钉复用任务目标、已选资料/仓库、约束和期望产物；追问恢复前文主题；仅在信息确实不足时澄清 | 至少 100 条中文路由与多轮用例，目标识别正确率 **≥95%**；本次复现的 5 类错误全部修复，不能无提示丢弃企业上下文 |
| P1.2 修复证据进入模型的过程 | 按正文块检索、选择和压缩，保留关键数字、表格关系、代码及来源；证据不足时补读或明确说明缺项 | 长文、表格、跨页、超预算用例全部检查关键事实是否仍可读取；不得把仅有元数据标记为已读取正文 |
| P1.3 建立真实评测和试点档案 | 从正常任务入口执行候选版本，读取实际发布答案；建立开发集与独立保留集；登记钉钉资料清单和三个仓库的运行档案 | 评测能区分答案错误、错误拒答、权限拒绝、模型失败和环境缺失；必需用例未执行时返回 **BLOCKED/NOT_RUN**，不能返回质量通过 |

**阶段交付：** 问答根因修复、首批中文保留集、真实 Run 评测驱动、试点资料与仓库档案、现状质量报告。P1 的答案验证先使用解析完整的固定资料，避免被 P2 尚未完成的格式覆盖影响。

### Phase P2：打通现有钉钉资料与三个云效仓库

**阶段目标：回答来自完整原文和真实源码，并能根据检索结果继续调查。**

| 目标 | 功能标准 | 自主验收与通过条件 |
|---|---|---|
| P2.1 钉钉资料完整可用 | 对固定试点清单逐项记录完整、部分、不支持、失败；处理其中实际出现的表格、编号、代码、图片或卡片；支持增量同步、删除和版本更新 | 清单内必需资料全部达到约定读取标准；不能通过删除失败资料缩小验收范围。至少 **60 条真实资料问题**，可回答问题正确率 **≥90%** |
| P2.2 云效源码进入调查链路 | Agent 经网关选择授权仓库、固定 commit/tree、搜索并读取文件；后续工具参数来自上一步结果；代码图与源码正文联合使用 | 至少 **40 条代码问题**，每仓库至少 10 条，覆盖入口、权限、业务链路、跨文件调用和历史变化；总体及各仓库正确率 **≥90%** |
| P2.3 可核查回答与统一权限传播 | 知识和代码均支持搜索→读取→补查→复核；引用定位到文档原文或 commit/path/line；权限变化影响历史、缓存、记忆和产物 | 引用支持对应事实的准确率 **≥95%**；错误拒答计失败；本地撤权立即阻断，外部权限同步最长 **5 分钟**且过期拒绝使用；并发撤权、跨组织和群受众反向用例全部通过 |

**阶段交付：** 可日常使用的企业知识与代码问答；钉钉与 Web 展示同一任务、同一最终答案及证据。当前知识补查循环扩展到代码调查，但继续使用同一个 Harness。

### Phase P3：真实沙箱、自主查改测与独立验收

**阶段目标：系统能够在三个试点仓库中完成有边界的开发任务，并交付可以重新验证的结果。**

| 目标 | 功能标准 | 自主验收与通过条件 |
|---|---|---|
| P3.1 真实隔离执行环境 | 接通 Linux Kubernetes＋gVisor；每任务独立固定版本副本；提供受治理文件、命令、日志、产物能力；默认拒绝网络，依赖由可信服务经网关获取 | 必须在真实集群验证隔离、网络策略和资源限制；宿主路径、凭据、其他项目及任意外网访问均被拒绝；取消后终止整个进程组并回收实例 |
| P3.2 自主任务闭环 | 在现有 Harness 内执行目标与完成条件→行动提议→授权→执行→验证→重规划；持久保存命令账本、检查点和执行代次，支持恢复与对账 | 三仓库合计至少 **40 项冻结任务**，每仓库至少 10 项；总体及各仓库独立完成率 **≥80%**；覆盖首次测试失败后自动修复、超时、取消、Worker 重启及响应丢失 |
| P3.3 独立验证与交付 | 在新建干净实例重放最终补丁，执行冻结验收；交付基础提交、差异、真实命令退出码、测试结果、未解决问题及复现方法 | 篡改测试、删除断言、伪造日志或退出码不能获得通过；预算耗尽或验证失败不得标记完成。成功经验仅形成候选，经过独立评测后才可推广 |

沙箱沿用既定默认限制：**2 vCPU、4 GiB 内存、10 GiB 临时磁盘、128 个进程**。源码传输必须适应三个仓库的实际规模，超限明确失败，不能静默截断。

需要通过 ADR 区分“控制面部署在生产环境”与“修改生产资源”：正式部署可以调度隔离开发沙箱，生产资源写入仍受禁止规则约束。

### Phase P4：完成企业问数与多源事故调查

**阶段目标：补齐蓝图要求的知识、数据、线上调查三个业务闭环。**

| 目标 | 功能标准 | 自主验收与通过条件 |

| P4.2 多源事故调查 | 关联 Metric、Log、Trace、Deployment、Git，必要时读取 Config；持久保存服务、仓库、发布与指标关系；区分相关线索、候选根因和已验证结论 | 至少 **20 个有金标事故案例**；已知根因 Top1 **≥80%**、Top3 **≥95%**；缺证据用例不能输出“已确认根因”。必要真实来源缺失时，本项保持未验收 |
| P4.3 报告与只读自动化 | 输出叙述、表格、图表、SQL、证据和报告；周期分析复用 Harness、身份、预算和通知治理 | 自动检查图表与查询结果一致；重复触发不重复产生逻辑任务；账户撤权后停止执行；失败、恢复和通知均有可核查记录 |

本阶段要求真实只读业务连接和跨源案例。开发适配器可以用于开发，但不能作为业务贯通的验收证据。

## 四、项目必须具备的自主验收机制

在现有评测模块和管理接口上扩展统一验收入口，例如：

```text
obsion acceptance run --phase P3 --profile staging --candidate <commit>
```

它必须自动完成以下过程：

1. **冻结输入。** 绑定源码、来源版本、镜像、模型、提示、能力版本、任务集及验收定义摘要。
2. **走真实入口。** 创建正常任务并等待终态，检查用户实际看到的答案、产物和工具执行结果。
3. **独立评分。** 知识使用预先审核的原文和要点；数据使用查询结果基准；代码使用干净环境中的冻结测试。不能直接采用被测 Run 自己的“VERIFIED”标记作为正确性得分。
4. **执行故障与安全用例。** 包含撤权、资料更新、群成员变化、模型不可用、工具超时、沙箱攻击、进程崩溃和不确定副作用。
5. **生成证据报告。** 输出逐项 PASS、FAIL、BLOCKED、NOT_RUN，以及原因、Run/Step/Policy/Evidence 引用、日志和产物摘要。
6. **阻止错误晋级。** 技术、安全、迁移硬门禁必须全部通过；业务质量按各阶段阈值判断。必需环境或用例缺失不能通过，不能降低标准、改题或移除失败案例后沿用旧成绩。

保留集按阶段扩充至至少 **200 项业务任务**：100 项知识与代码问答、40 项项目任务、40 项问数、20 项事故调查；另设安全、恢复及权限反向测试集。

可回答问题的正确率分母包含全部可回答任务，错误拒答计失败；无资料时正确说明不足单独评分，防止靠大量拒答提高成绩。

## 五、接口、预算与阶段交付约束

- **兼容扩展：** 在既有 Run/Step/Event 和评测接口上增加任务完成条件、结构化行动、沙箱命令记录、检查点和独立验收结果；保留旧客户端、事件和离线评测契约。新增语义质量指标，避免继续混用引用关联有效率与事实正确率。
- **默认预算：** 知识任务最多 12 个工具步骤、2 分钟、2 万 token；项目任务最多 40 步、30 分钟、10 万 token；自动重规划最多 3 次；普通命令 120 秒，测试命令最多 600 秒。无进展或超限保存进度并明确结束原因。
- **交付要求：** 每阶段包含实现、测试、文档、迁移或无需迁移说明、验证报告、架构门和必要 ADR，并更新项目状态。生产数据库变更需有真实迁移、升级和恢复证据。
- **执行顺序：** P1→P2→P3→P4→P5；身份、审计和可靠性建设从 P1 并行开展，不能等到 P5 才补安全基础。
- **完成定义：** 自主技术验收通过后，系统可以证明对应能力达到约定标准；正式上线仍必须满足既有 Phase 99 门禁及真实安全、数据负责人和发布授权，Agent 不得自行生成批准记录。
