# Obsion 0.83.0-dev Alpha.1 release-candidate hardening

This phase closes the repository-side Alpha.1 candidate gap. A clean CI revision now
builds every distributable class, validates each in an isolated environment, checks
the Alpha.1 requirements matrix against the exact artifact identities, and retains a
content-addressed manifest plus candidate report. It does not publish or promote the
release.

## Candidate evidence

The candidate path is deliberately stricter than a developer build:

1. `scripts/release_artifacts.py build` refuses a dirty source tree. The explicit
   `--allow-dirty` escape hatch records `sourceClean: false`; candidate validation
   rejects that manifest.
2. File artifacts carry SHA-256 hashes. Container artifacts carry their local
   `sha256:` image id as both identity and digest. No artifact class may be skipped.
3. Clean-room validation exports hash-pinned runtime dependencies from `uv.lock`,
   installs them and the four wheels into a fresh venv, checks dependency consistency,
   and then performs CLI imports, Node ESM import, Java class loading, control-plane
   image import, and Workbench HTTP startup.
4. `docs/release/alpha1-candidate-gates.yaml` maps every unique row in the V1
   requirements matrix exactly once to expected artifact identities and real test
   evidence. Missing, duplicate, or stale mappings fail CI.
5. The CI candidate job depends on quality, migration, Java SDK, and Helm jobs,
   repeats artifact build/validation from the checked-out revision, runs Trivy on the
   exact local image tags, and uploads `dist/release/` for fourteen days.

The retained `release-candidate-report.json` reports repository evidence separately
from production authority. With the current gate document it must say
`promotion_eligible: false` and list all pending operator gates.

## Operator boundary

Phase 83 explicitly defers rather than simulates:

- clean-infrastructure staging and UAT;
- timed PostgreSQL and object-storage restore drills;
- registry HIGH/CRITICAL CVE policy and signed image promotion;
- live OIDC, external secret manager, and read-only replicas;
- security and data-owner approval;
- maintainer-authorized signed tag/package/image publication.

A pending gate cannot contain evidence or approval metadata. A satisfied gate must
contain real repository evidence plus accountable approval metadata. The optional
`--require-promotion-eligible` mode fails until all six gates are satisfied.

## Architecture and migration

There is no runtime, API, Event, Capability, Policy, credential, or database change.
The durable Harness remains Workspace → Thread → Turn → Run → Step → Event, and all
external execution remains behind Capability Gateway and Policy. No Alembic revision
is added.

## Verification


Full artifact candidate validation is intentionally a clean-checkout CI path:

```bash
make release-artifacts
make validate-release-artifacts
make validate-release-candidate
```

The same path was exercised in an isolated clean local git snapshot during Phase 83:
12 artifacts built, 21 validation steps passed, and the candidate report covered all
37 requirement rows while correctly retaining all six operator gates as pending.

None of these commands reads vendor credentials or the external `worker.txt` and
`ci.txt` files.
