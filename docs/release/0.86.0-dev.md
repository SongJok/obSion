# Obsion 0.86.0-dev Alpha.1 artifact-store drill evidence

Phase 85 proved the PostgreSQL half of the recovery story; this phase records
the object-storage half. One opt-in drill migrates a throwaway PostgreSQL
container with Alembic, seeds knowledge and file artifacts through the real
control-plane REST API into a throwaway MinIO container, snapshots the source
bucket into a canonical per-object manifest with SHA-256 checksums, restores
the snapshot into a fresh bucket on a second throwaway MinIO container, and
verifies key-set, content-checksum, metadata, and database-reference parity.
The outcome is a second redacted, checksummed ledger that the Alpha.1 candidate
gate validates offline alongside the PostgreSQL drill ledger.

## Artifact drill evidence ladder

`docs/release/alpha1-artifact-drill-evidence-contract.yaml` declares eight
ordered checks against the pinned `quay.io/minio/minio:RELEASE.2025-04-22T22-12-26Z`
and `pgvector/pgvector:0.8.6-pg17-bookworm` images (the same images
docker-compose runs):

1. `source-migrated` — `alembic upgrade head` completes on the drill database.
2. `objects-seeded` — a knowledge document and a workspace file artifact
   uploaded through the real REST API land in the source bucket with persisted
   database storage references, meeting the minimum object threshold.
3. `snapshot-created` — every source object is captured to a local snapshot
   directory with its size, SHA-256, content type, and user metadata recorded
   in a canonical manifest.
4. `restore-completed` — every snapshot payload is written from disk into a
   fresh bucket on a second throwaway MinIO container.
5. `object-count-parity` — the restored key set is identical to the manifest.
6. `content-checksum-parity` — every restored object matches its snapshot
   SHA-256.
7. `metadata-parity` — every restored object preserves content type and user
   metadata (including the stored `sha256` and `classification` headers).
8. `database-consistency` — every `artifacts.storage_key` and
   `document_versions.content_ref` row resolves to a restored object whose
   SHA-256 matches the database checksum.

`OBSION_DR_DRILL=1 make record-artifact-drill-evidence` (or
`obsion record-artifact-drill-evidence`) runs the ladder and writes
`docs/release/evidence/alpha1/artifact-store-drill.yaml`. Once a stage fails,
every downstream check is recorded `failed` — a skip is never a pass. Drill
credentials are generated per run, never leave process memory, and never appear
in the ledger; containers and the snapshot directory are removed in every
outcome.

## Explicit object-store backend selection

`Settings.object_store_backend` (`OBSION_OBJECT_STORE_BACKEND`) selects the
artifact backend: `auto` (default) preserves the historical behaviour —
in-memory under `TEST`, MinIO otherwise — while `memory` and `minio` force a
backend in any environment. The drill seeds with `minio` under `TEST` so the
dumped bucket reflects the production `MinioObjectStore` write path without
flipping the rest of the environment (rate limiting, auth, model gateway) off
its test posture.

## Candidate-gate binding

The candidate contract's `drillEvidence` section becomes a `ladders` list so
each drill family binds its own contract and ledgers:
`validate-release-candidate` dispatches on the ladder kind, validates both
ledgers offline, and reports `drill_evidence_ledgers: 2` and
`drill_evidence_checks: 16`. Recorded drill evidence never feeds
`promotion_eligible`: the staging-scoped `backup-restore-drill` operator gate
remains PENDING with the other five gates.
