# Obsion 0.87.0-dev Alpha.1 drill CI signal

ADR 0064 noted the repository had no CI-detectable signal when the restore path
breaks; the Phase 85 PostgreSQL drill immediately proved the value of such a
signal by surfacing a latent trigger defect. This phase closes the gap:
`.github/workflows/drill.yml` runs both drill ladders nightly (and on manual
dispatch) on docker-capable hosted runners, so a restore-path regression turns
red within one schedule tick instead of waiting for the next operator
recording.

## What the workflow does

- Triggers: nightly schedule plus `workflow_dispatch`. It is deliberately not
  a pull-request gate — the drills pull pinned registry images, and external
  registry health must never block a merge.
- Runs `obsion record-drill-evidence` and
  `obsion record-artifact-drill-evidence` with `OBSION_DR_DRILL=1`, writing
  fresh ledgers to `$RUNNER_TEMP`. Committed operator-recorded ledgers under
  `docs/release/evidence/alpha1/` are never touched by automation; their
  provenance stays bound to the recording commit.
- The recorders' fail-closed semantics are the signal: any failed check exits
  non-zero and the job goes red.
- Fresh ledgers are uploaded as CI artifacts with 14-day retention for
  debugging; they contain counts, timings, and SHA-256 digests only — no
  credentials, endpoints, or object keys.
- The workflow requests `contents: read` only and carries no vendor
  credentials, no secrets, and no publish/push steps.

## Boundaries

The CI drill is a detection signal, not new evidence authority: it does not
refresh the committed ledgers, does not feed `promotion_eligible`, and leaves
all six operator gates PENDING. Refreshing recorded evidence remains an
explicit operator action (`make record-drill-evidence`,
`make record-artifact-drill-evidence`).
