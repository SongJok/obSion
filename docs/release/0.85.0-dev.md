# Obsion 0.85.0-dev Alpha.1 backup/restore drill evidence

This phase turns the backup/restore runbook from prose into executed, recorded
evidence. One opt-in drill migrates a throwaway PostgreSQL container with
Alembic, seeds a real governed Harness scenario through the control-plane REST
API, takes a custom-format `pg_dump`, restores it into a fresh container, and
verifies schema-version, row-count, referential-integrity, and audit-identity
parity. The outcome is a redacted, checksummed ledger that the Alpha.1 candidate
gate validates offline. The drill also caught — and this phase fixes — a latent
PostgreSQL trigger defect that failed every `verification_assessments` insert.

## Drill evidence ladder

`docs/release/alpha1-drill-evidence-contract.yaml` declares eight ordered checks
against the pinned `pgvector/pgvector:0.8.6-pg17-bookworm` image (the same image
docker-compose runs):

1. `source-migrated` — `alembic upgrade head` completes on the drill source.
2. `dataset-seeded` — a workspace, knowledge document, thread, and completed
   governed Run created through the real REST API meet minimum row thresholds
   across the Harness, Evidence, Claim, and audit tables.
3. `dump-created` — `pg_dump --format=custom` produces a non-empty backup with a
   recorded SHA-256.
4. `restore-completed` — `pg_restore --exit-on-error` into a fresh, empty target
   exits cleanly.
5. `schema-version-parity` — the restored `alembic_version` matches the source
   head.
6. `row-count-parity` — every public table count is identical between source and
   target (89 tables in the recorded drill).
7. `referential-integrity` — no orphaned steps, events, turns, or threads.
8. `audit-preserved` — ordered audit log identities are non-empty and identical
   after restore.

`OBSION_DR_DRILL=1 make record-drill-evidence` (or
`obsion record-drill-evidence`) runs the ladder and writes
`docs/release/evidence/alpha1/backup-restore-drill.yaml`. Once a stage fails,
every downstream check is recorded `failed` — a skip is never a pass. Drill
credentials are generated per run, never leave process memory, and never appear
in the ledger; containers are removed in every outcome.

## Latent trigger defect found and fixed

The first drill run failed `dataset-seeded` because the deferred
verification-admission trigger resolved its candidate id through one SQL `CASE`
expression referencing `NEW.assessment_id`. plpgsql validates that field
reference against the trigger row type when the expression is planned, so every
insert into `verification_assessments` — a table without `assessment_id` —
failed at COMMIT. Alembic revision `b88f1c4d5e60` replaces the function body
with branch statements whose field references are only planned when the branch
executes; the verification logic is byte-identical otherwise. The downgrade
restores the historical body, and the drill's green ledger now proves a real
governed Run completes against migrated PostgreSQL 17.

## Candidate-gate binding

`docs/release/alpha1-candidate-gates.yaml` gains a `drillEvidence` section;
`validate-release-candidate` verifies the ledger offline (schema, checksum,
redaction, minimum rows, all eight checks passed) and reports
`drill_evidence_ledgers` and `drill_evidence_checks`. Recorded drill evidence
never feeds `promotion_eligible`: the staging-scoped `backup-restore-drill`
operator gate remains PENDING with the other five gates.
