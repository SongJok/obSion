# Obsion 0.94.0-dev Alpha.1 automation Web authoring depth

Since the early phases the automation backend enforced the full
workflow lifecycle — immutable versions, per-version publishing,
trigger payloads with idempotency, schedules with misfire policy and
fixed-version pinning, retire, and step output references — but the
Workbench exposed only the happy path. Phase 94 closes that authoring
depth gap entirely on the client side: no backend route, schema, or
permission changes.

## What changed

- **Versions card**: every version listed newest-first with step
  summary, checksum prefix, and publish state; inspect,
  derive-new-version, and publish/rollback actions per row.
- **Spec viewer**: read-only rendering of a version's step DAG with
  prompts, review instructions, self-review flag, and notification
  content.
- **Derived authoring**: new versions prefill from any existing spec
  through the shared `buildSpecFromDraft` builder the create modal now
  also uses.
- **Trigger payloads**: manual runs accept a validated JSON object;
  idempotency keys keep the existing `web-{uuid}` generation.
- **Schedule authoring**: post-creation schedules with cron presets or
  validated custom expressions, timezone, misfire policy,
  fixed-version pinning, and input payloads.
- **Retire**: guarded two-step retire for PAUSED workflows.
- **Provenance**: step output refs render as labeled chips and child
  Harness runs open in the Runtime inspector through the existing
  `openRunInspection` path.

## Compatibility and migration

None. The automation API contract is unchanged; the Workbench simply
exposes what it already enforced. Rollback is reverting the phase
commits.

## Known limitations

- Schedules remain enable/disable only after creation; editing a
  schedule means creating a new one (matching the backend contract).
- Step artifact refs render as labeled chips; opening the artifact
  itself stays in the Artifacts view.
- All six Alpha.1 candidate gates remain PENDING operator-owned items.
